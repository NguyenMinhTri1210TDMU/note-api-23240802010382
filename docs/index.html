3 Năm đặc trưng thiết yếu của điện toán đám mây theo NIST

🖥️

1. On-demand self-service

Người dùng có thể tự cung cấp tài nguyên tính toán như máy chủ, dung lượng lưu trữ và mạng khi cần mà không cần tương tác trực tiếp với nhà cung cấp dịch vụ.

🌐

2. Broad network access

Dịch vụ được truy cập thông qua mạng bằng các cơ chế tiêu chuẩn, hỗ trợ nhiều loại thiết bị như máy tính, điện thoại và máy tính bảng.

📦

3. Resource pooling

Tài nguyên của nhà cung cấp được gom lại để phục vụ nhiều khách hàng theo mô hình multi-tenant, phân bổ linh hoạt theo nhu cầu.

⚡

4. Rapid elasticity

Tài nguyên có thể được mở rộng hoặc thu hẹp nhanh chóng theo nhu cầu. Đối với người dùng, tài nguyên có thể được xem như không giới hạn.

📊

5. Measured service

Việc sử dụng tài nguyên được đo lường, giám sát và báo cáo, giúp người dùng và nhà cung cấp kiểm soát mức tiêu thụ dịch vụ.

7.2. Dockerfile

Dockerfile sử dụng image nền Node.js 22 Alpine, cài đặt các dependency cần thiết, sao chép mã nguồn và chạy ứng dụng bằng tài khoản không phải root.

FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY src ./src

ENV PORT=3000
EXPOSE 3000

USER node

CMD ["node", "src/server.js"]

Loại bỏ các thư mục và tệp không cần thiết khỏi build context để giảm dữ liệu gửi đến Docker khi build image.

7.4. Build Docker image

docker build -t notes-api:1.0 .

Image được build thành công với các thông tin ghi nhận:

7.5. Chạy hai container

Khởi chạy hai container từ cùng một image. Container thứ nhất sử dụng cấu hình mặc định; container thứ hai được giới hạn CPU ở mức 0.5 và RAM 128 MB.

docker run -d --name notes1 -p 3000:3000 notes-api:1.0

docker run -d --name notes2 -p 3001:3000 \
  --cpus=0.5 \
  --memory=128m \
  notes-api:1.0

Kiểm tra hai API:

curl -s localhost:3000
curl -s localhost:3001

Cả hai container đều phản hồi API thành công. Việc ánh xạ cổng giúp truy cập hai instance riêng biệt từ Codespaces.

7.6. Kiểm tra giới hạn tài nguyên

Sử dụng docker stats để quan sát mức sử dụng tài nguyên thực tế:

docker stats --no-stream
ContainerCPUMemory usageMemory limitMemory %
notes10.00%13.15 MiB7.756 GiB0.17%
notes20.00%12.71 MiB128 MiB9.93%

Kiểm tra cấu hình giới hạn bằng docker inspect:

docker inspect notes2 --format \
'Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}'

Kết quả:

Memory=134217728 bytes
NanoCpus=500000000

134217728 bytes tương đương 128 MiB; NanoCpus=500000000 tương ứng 0.5 CPU. Đây là bằng chứng Docker đã áp dụng giới hạn cấu hình cho notes2.

7.7. Giải thích kết quả

Docker sử dụng cgroups để kiểm soát tài nguyên mà container được phép sử dụng. Tuy nhiên, API Node.js trong bài thực hành sử dụng các hàm như os.totalmem() để đọc thông tin hệ thống. Giá trị trả về có thể phản ánh RAM của host thay vì giới hạn cgroup được đặt cho container. Vì vậy, cần phân biệt giữa thông tin hệ thống mà ứng dụng hiển thị và giới hạn tài nguyên thực tế do Docker áp dụng.

8 Đưa Docker image lên GitHub Container Registry

8.1. Đăng nhập GHCR

Sử dụng Personal Access Token được lưu trong Codespaces Secret với tên CR_PAT. Không ghi token trực tiếp vào mã nguồn hoặc báo cáo.

echo "$CR_PAT" | docker login ghcr.io \
  -u NguyenMinhTri1210TDMU --password-stdin

Đăng nhập thành công vào GitHub Container Registry.

8.2. Gắn tag và push image

docker tag notes-api:1.0 \
  ghcr.io/nguyenminhtri1210tdmu/notes-api:1.0

docker push \
  ghcr.io/nguyenminhtri1210tdmu/notes-api:1.0

Image được đẩy lên GHCR thành công với thông tin:

Packagenotes-api
Tag1.0
Digestsha256:245aad379084...

Đường dẫn package:

GitHub Container Registry – notes-api

Package đã được chuyển sang chế độ Public để có thể pull image mà không cần xác thực.

8.3. Kiểm tra pull image công khai

Xóa image cục bộ, sau đó pull lại image từ GHCR để xác minh package có thể được tải xuống và triển khai.

docker rmi notes-api:1.0 \
  ghcr.io/nguyenminhtri1210tdmu/notes-api:1.0

docker pull \
  ghcr.io/nguyenminhtri1210tdmu/notes-api:1.0

docker run -d --name notes-public-test \
  -p 3000:3000 \
  ghcr.io/nguyenminhtri1210tdmu/notes-api:1.0

curl -s localhost:3000

Đã xóa image cục bộ, pull lại image từ GHCR và chạy container kiểm thử công khai thành công. Kết quả chứng minh image có thể được phân phối và triển khai từ registry mà không cần build lại từ mã nguồn.

10.3. Phân tích từng lần chạy

  • Run 0: Hai VM có tổng cộng 8 PEs, đáp ứng nhu cầu 4 Cloudlet, mỗi Cloudlet cần 2 PEs. Cả 4 Cloudlet hoàn thành với thời gian thực thi 20.0 giây; bắt đầu tại 0.1 giây và kết thúc tại 20.1 giây.
  • Run 1: Khi tăng lên 4 VM, mỗi VM yêu cầu 4 PEs, tổng nhu cầu là 16 PEs trong khi Host chỉ có 8 PEs. Vì vậy chỉ 2 VM được cấp phát, 2 VM còn lại không thể tạo. Bốn Cloudlet vẫn hoàn thành trên hai VM được cấp; thời điểm bắt đầu bị lùi do thời gian thử cấp phát lại.
  • Run 2: Tám Cloudlet được gửi đến hai VM. Mỗi VM có RAM 512 MB và BW 1000 Mbps; mô hình sử dụng tài nguyên 0.5. Hệ thống cảnh báo Cloudlet 4–7 không được cấp đủ 256 MB RAM và 500 Mbps BW. Chỉ Cloudlet 0–3 hoàn thành tại 40.1 giây; không được kết luận cả 8 Cloudlet hoàn thành.
  • Run 3: Đổi Cloudlet scheduler sang CloudletSchedulerSpaceShared. Với 4 PEs mỗi VM và mỗi Cloudlet cần 2 PEs, hai Cloudlet có thể chạy đồng thời trên mỗi VM. Do đó kết quả lần chạy này trùng baseline; điều này chỉ đúng với workload cụ thể, không có nghĩa hai scheduler luôn tương đương.

10.4. Phân biệt hai scheduler

VmSchedulerSpaceShared quyết định cách Host phân bổ PEs cho VM. CloudletSchedulerTimeShared hoặc CloudletSchedulerSpaceShared quyết định cách VM phân bổ CPU cho Cloudlet bên trong VM. Đây là hai tầng lập lịch khác nhau.

11 Câu hỏi bảo vệ và trả lời

1. Vì sao API trong notes2 vẫn báo RAM của host dù container bị giới hạn 128 MB?

Vì API Node.js đang đọc thông tin hệ thống qua os.totalmem(), có thể trả về RAM của host thay vì giới hạn cgroup. Docker vẫn áp dụng giới hạn 128 MiB, thể hiện qua docker stats và docker inspect. Ứng dụng cần đọc thông tin cgroup phù hợp (cgroup v2/v1) hoặc dùng thư viện nhận biết container để tính tài nguyên khả dụng.

2. Time-shared và Space-shared khác nhau thế nào? Nhà cung cấp cloud nên chọn gì cho gói giá rẻ?

Time-shared chia sẻ CPU giữa nhiều Cloudlet theo thời gian; Space-shared cấp PE cho Cloudlet và chỉ chạy khi đủ PE. Gói giá rẻ hướng đến tận dụng tài nguyên có thể chọn Time-shared để tăng mức chia sẻ và thông lượng tổng thể, nhưng cần kiểm soát hiệu năng và tránh overcommit quá mức. Space-shared phù hợp hơn khi cần phân bổ PE rõ ràng và hiệu năng dễ dự đoán.

3. Mô phỏng có lợi ích và hạn chế gì so với hạ tầng thật?

Mô phỏng giúp thử nhiều cấu hình, quan sát lập lịch và phân bổ tài nguyên với chi phí thấp, có thể lặp lại. Tuy nhiên, kết quả phụ thuộc mô hình và giả định; không phản ánh đầy đủ độ trễ mạng, lỗi phần cứng, nhiễu tải và hành vi thực tế. Vì vậy nên dùng mô phỏng để phân tích ban đầu, sau đó kiểm chứng bằng benchmark trên hạ tầng thật.
